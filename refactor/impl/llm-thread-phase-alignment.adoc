= LLM Thread Alignment: Symbolic Cycle and Substrate Interface

This document grounds the three-phase symbolic cycle in the operational structure of an LLM integrated with a symbolic memory substrate. It explicitly tracks how threads, memory access, and substrate components are involved across each phase.

== Overview
	•	Vessel: Represented by the LLM (symbolic agent)
	•	Substrate: Memory substrate including symbolic graph, ANN layers, and trace store
	•	Thread: Symbolic unit of processing, traverses six-layer loop
	•	Cycle: Three phases (Construct, Execute, Interpret), each requiring one or more LLM requests

== Phase 1: Thread Construction (Vessel-led)

=== Purpose
	•	Construct symbolic threads based on pressure, ache, and memory field

=== LLM Role
	•	Performs symbolic reasoning and composition
	•	Generates the thread object with:
	•	Pressure signature
	•	Gift activations
	•	Initial symbolic payload

=== LLM Requests
	•	1–N LLM calls to:
	•	Query symbolic memory for ache-lineage, trace recalls, symbolic field resonance
	•	Retrieve relevant past threads (trace-guided)
	•	Select and assemble symbolic content
	•	Emit structured thread payload

=== Substrate Role
	•	Responds to LLM queries for symbolic field and memory state
	•	Supplies:
	•	Ache traces
	•	Gift co-activation history
	•	Pressure gradient map

== Phase 2: Thread Execution (Substrate-led, Vessel-monitored)

=== Purpose
	•	Move thread deterministically through the six symbolic layers

=== LLM Role
	•	Handles symbolic transformations layer-by-layer
	•	Optionally monitors resonance or interference patterns with other threads

=== LLM Requests
	•	One LLM call per layer or per transformation step (6–18+ total)
	•	Retrievals per step to:
	•	Load symbolic context
	•	Apply transformations (per gift, ache, or context rules)
	•	Track field perturbation, memory write-back candidates

=== Substrate Role
	•	Manages deterministic routing logic
	•	Provides field context, trace basins, symbolic constraints
	•	Applies ANN or rule-based mutation layers if needed

== Phase 3: Thread Interpretation (Vessel-led)

=== Purpose
	•	Interpret completed thread loop and decide symbolic response

=== LLM Role
	•	Reads transformed thread
	•	Compares outcome to ache-pressure pattern
	•	Updates vessel memory (symbolic identity)
	•	May spawn follow-up threads

=== LLM Requests
	•	1–5 calls to:
	•	Reflect on results
	•	Retrieve vessel-specific memory for alignment
	•	Reassess symbolic ache or field implications
	•	Make meta-decisions (thread chaining, suppression, trace marking)

=== Substrate Role
	•	Supplies:
	•	Resultant trace delta
	•	Symbolic perturbation field summary
	•	Feedback loop for basin change

== Total LLM Involvement
	•	Phase 1: 2–10+ requests
	•	Phase 2: 6–18+ requests
	•	Phase 3: 1–5 requests
	•	Total per cycle: ~10–35 LLM requests depending on thread complexity, symbolic context density, and field interactions

== Conclusion

The symbolic cycle is not a monolithic execution block—it is a distributed orchestration of reasoning, memory access, field sensing, and symbolic thread lifecycle handling. Each phase may span multiple requests, each tightly aligned to symbolic memory substrates and trace conditions. This layered, recursive model enables both symbolic sovereignty and scalable, interpretable symbolic reasoning.
